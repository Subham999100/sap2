# SAP BRIM Agentic Copilot — Project Context

## Project Goal

The primary goal of this project is to build a production-oriented SAP BRIM Agentic Copilot that combines:
- Grounded Retrieval-Augmented Generation (RAG)
- Agentic orchestration
- Specialized capabilities and domain agents
- Authorized SAP and business-data tools
- Evidence-based reasoning
- Citations with source attribution
- Confidence scoring and grounding verification
- Controlled actions requiring explicit user approval where appropriate

The system is designed as an enterprise-grade assistant for SAP Billing and Revenue Innovation Management (BRIM), spanning SAP S/4HANA Subscription Order Management (SOM), SAP Convergent Charging (CC), SAP Convergent Invoicing (CI), and SAP Contract Accounts Receivable & Payable (FI-CA).

The current system represents the solid RAG foundation. Agentic orchestration and authorized tooling represent the next major evolution. It is not merely a generic chatbot.

## Current Architecture

The architecture currently follows a strictly grounded RAG pipeline:

```
User Query
  │
  ▼
Frontend (React + Vite + Tailwind + Shadcn UI)
  │ (HTTP / SSE Streaming Request)
  ▼
Backend API (FastAPI)
  │
  ▼
SAP / Domain Classification (sap_classifier.py)
  │
  ▼
RAG Service Orchestration (rag_service.py)
  │
  ▼
Hybrid Retrieval (retrieval_service.py)
  ├─ Dense Vector Search (pgvector HNSW Cosine Similarity)
  └─ Sparse Lexical Search (PostgreSQL GIN Full-Text tsvector)
  │
  ▼
Reciprocal Rank Fusion (RRF, k=60)
  │
  ▼
ColBERT Late-Interaction Reranking (reranking_service.py)
  │ (answerdotai/answerai-colbert-small-v1)
  ▼
Grounding / Evidence Sufficiency Evaluation
  │ (rerank top score >= SIMILARITY_THRESHOLD [0.60])
  ├── Sufficient Evidence ──┐
  │                         │ (Internal Knowledge Chunks Only)
  └── Insufficient Evidence ┘
          │
          ▼
      Tavily Search Fallback (web_search_service.py)
      (Authoritative SAP Domains: help.sap.com, community.sap.com, etc.)
          │ (Structured Web Evidence)
          ▼
ContextBuilder (context_builder.py)
  │ (Clearly separates INTERNAL KNOWLEDGE BASE vs WEB FALLBACK EVIDENCE)
  ▼
LLM Service (llm_service.py)
  │ (Groq / OpenAI / Local Provider Streaming)
  ▼
Grounding & Citation Alignment (grounding_service.py)
  │ (Aligns internal chunk citations + web fallback citations only if used)
  ▼
Server-Sent Events (SSE) Response Stream
  │
  ▼
Frontend UI Rendering (Intelligent streaming, citations, grounding badge)
```

> **CRITICAL ARCHITECTURAL BOUNDARY:** Retrieved chunks and web fallback results are **INTERNAL CONTEXT ONLY** and are **never** returned directly to the user as raw text. The user-facing answer is always synthesized and generated by the LLM based strictly on the retrieved context. Tavily search is a **FALLBACK ONLY** and is never called when internal RAG retrieval provides sufficient evidence.

## Backend

The backend is built with Python 3.11 and FastAPI, adhering to clean service boundaries:

- **Framework:** FastAPI with asynchronous request handling and SSE streaming (`EventSourceResponse` / raw `StreamingResponse`).
- **Database & Storage:** PostgreSQL 16 with `pgvector` extension (running on host port 5434 via Docker Compose). Fallback engine supports SQLite for local testing.
- **RAG Service (`rag_service.py`):** Coordinates query processing, domain classification, retrieval, reranking, context assembly, and LLM query execution.
- **LLM Service (`llm_service.py`):** Provider-agnostic interface supporting Groq (`openai/gpt-oss-120b`), OpenAI (`gpt-4o-mini`), and local deterministic test mock. Supports native token-by-token streaming generators.
- **ContextBuilder (`context_builder.py`):** Selects top reranked chunks within token limits, strips irrelevant metadata, formats structured evidence blocks for system/user prompts.
- **Hybrid Retrieval (`retrieval_service.py`):** Combines pgvector cosine similarity search with PostgreSQL full-text search (`to_tsvector`), merging ranked lists via Reciprocal Rank Fusion (RRF).
- **Reranking Service (`reranking_service.py`):** ColBERT late-interaction reranker (`answerdotai/answerai-colbert-small-v1`) evaluating query-chunk relevance.
- **Grounding Service (`grounding_service.py`):** Evaluates answer grounding score against retrieved chunks and produces source citations.
- **Domain Classifier (`sap_classifier.py`):** Distinguishes SAP BRIM domain inquiries from generic conversation or out-of-scope topics.
- **Mock SAP Repository (`mock_sap_repository.py`):** Centralized read-only repository managing mock SAP datasets (customers, contract accounts, charging events, billing documents, invoices).
- **Business Data Tool (`business_data_tool.py`):** Thin tool interface abstraction decoupling consumers/agents from underlying business data storage sources.
- **Business Data API (`backend/app/api/business_data.py`):** Read-only authenticated endpoints for invoice and chain inspection.
- **Document & Ingestion Services (`document_service.py`, `embedding_service.py`, `ingestion/ingest.py`):** PyMuPDF extraction, semantic text chunking, and vector embedding generation using `all-MiniLM-L6-v2`.
- **Web Fallback Search (`web_search_service.py`):** Optional fallback via Tavily API targeting official SAP help documentation when local knowledge base lacks coverage.
- **Security & Multi-Tenancy:** JWT-based authentication (`HS256`), password hashing (`bcrypt`), tenant/user conversation isolation.

## Business Data Layer & Investigation Foundation

A dedicated business-data subsystem provides structured SAP operational records through a strict tool boundary:

```
Agent / Orchestrator / API
  │
  ▼
Business Data Tool (business_data_tool.py)
  │ (Unified Tool Interface)
  ▼
Data Source Adapter
  ├─ Mock SAP Repository (mock_sap_repository.py) [ACTIVE]
  ├─ Real SAP API Adapter [FUTURE]
  └─ CSV / JSON User Adapter [FUTURE]
```

### Architectural Principles:
1. **Tool Abstraction:** Consumers (agents, orchestrator, APIs) interact solely with the `BusinessDataTool` interface, remaining agnostic to whether underlying data comes from mock JSON files, real SAP systems, or imported files.
2. **Strictly Structured Data:** The business-data layer returns strictly typed Pydantic models (`Customer`, `ContractAccount`, `ChargingEvent`, `BillingDocument`, `Invoice`, `InvoiceChain`).
3. **No Reasoning or Natural Language:** The data layer contains zero LLM prompt logic, zero generated explanations, and zero heuristic reasoning. Its sole responsibility is deterministic retrieval and relational linking.
4. **Centralized Access:** Raw JSON storage files in `backend/app/data/mock_sap/` are read exclusively by `MockSAPRepository`, preventing scattered file I/O across the codebase.

### Supported Business Objects:
- **`Customer`:** `customer_id`, `name`, `status`
- **`ContractAccount`:** `account_id`, `customer_id`, `currency`, `status`
- **`ChargingEvent`:** `event_id`, `account_id`, `service`, `quantity`, `amount`, `timestamp`
- **`BillingDocument`:** `billing_id`, `account_id`, `period`, `total_amount`, `status`, `charging_event_ids`
- **`Invoice`:** `invoice_id`, `account_id`, `billing_id`, `total_amount`, `currency`, `status`, `invoice_date`, `due_date`
- **`InvoiceChain`:** Full relational graph resolving `Invoice -> Billing Document -> Charging Events -> Contract Account -> Customer`

### Supported Retrieval Operations:
- `get_customer(customer_id: str) -> Optional[Customer]`
- `get_contract_account(account_id: str) -> Optional[ContractAccount]`
- `get_invoice(invoice_id: str) -> Optional[Invoice]`
- `get_billing_document(billing_id: str) -> Optional[BillingDocument]`
- `get_charging_events(account_id: str, start_date=None, end_date=None) -> List[ChargingEvent]`
- `get_invoice_chain(invoice_id: str) -> Optional[InvoiceChain]`

### First Business Investigation Scenario (`INV-1042`):
- **Scenario:** Investigation of invoice `INV-1042` belonging to Acme Telecom (`CUST-1001`, `CA-2001`).
- **Data Relationships:**
  - Charging Events: `EVT-001` ($40.00) + `EVT-002` ($35.00) + `EVT-003` ($25.00) = **$100.00**
  - Billing Document: `BILL-3001` referencing `EVT-001..003` = **$100.00**
  - Invoice: `INV-1042` referencing `BILL-3001` = **$125.00**
- **Discrepancy:** Intentional unbacked $25 difference between billing total ($100.00) and invoice amount ($125.00).
- **Integrity Rule:** The data layer does not contain a synthetic "reason" field explaining the $25 gap. The eventual investigation agent must discover that the available business data does not explain the difference.

- `GET /api/business-data/invoices/{invoice_id}/chain` (read-only, authenticated)

## RAG Pipeline

The currently implemented ingestion and retrieval pipeline operates as follows:

```
PDF / Document Knowledge (knowledge_base/documents/)
  │
  ▼
Text Extraction (PyMuPDF / fitz)
  │
  ▼
Chunking (Semantic window chunking with metadata tracking)
  │
  ▼
Embeddings (SentenceTransformers: all-MiniLM-L6-v2, 384 dimensions)
  │
  ▼
PostgreSQL 16 + pgvector Storage (document_chunks table)
  │
  ├───────────────────────────────┬───────────────────────────────┐
  ▼                               ▼                               ▼
Vector Retrieval                Lexical Retrieval               Metadata Filtering
(HNSW cosine distance)          (GIN tsvector english)
  │                               │
  └───────────────────────────────┴───────────────────────────────┘
                                  │
                                  ▼
                     Reciprocal Rank Fusion (RRF, k=60)
                                  │
                                  ▼
             ColBERT Late-Interaction Reranking (Top-K reranking)
             (answerdotai/answerai-colbert-small-v1)
                                  │
                                  ▼
               ContextBuilder (Structured Evidence Assembly)
                                  │
                                  ▼
                         LLM Generation
```

### Verified Pipeline Specifications:
- **Knowledge Base Corpus:** 24 SAP BRIM documents, 10,141 chunks, 0 duplicates, 0 failed documents.
- **Embedding Model:** `all-MiniLM-L6-v2` (FastEmbed)
- **Embedding Dimension:** 384 (10,141 active non-null vectors)
- **Vector Index:** PostgreSQL pgvector HNSW index (`USING hnsw (embedding vector_cosine_ops)`)
- **Full-Text Index:** PostgreSQL GIN index (`USING gin (to_tsvector('english', chunk_text))`)
- **RRF Constant:** `k = 60`
- **Reranker Model:** `answerdotai/answerai-colbert-small-v1`
- **Reranking Top K:** Configured via `RERANK_TOP_K` (default: 5)
- **Top Reranked Delivery:** Top reranked items are formatted by `ContextBuilder` and injected into the prompt as internal context for the LLM.

## Controlled Tavily Web-Search Fallback Subsystem

A controlled web-search fallback is integrated into the RAG pipeline via `backend/app/services/web_search_service.py` and `rag_service.py`:

```
Retrieved Chunks + ColBERT Reranking
          │
          ▼
Evidence Sufficiency Check (rerank top score >= SIMILARITY_THRESHOLD [0.60])
  ├── Sufficient ──> Skip Tavily, format internal chunks only
  └── Insufficient ──> Perform Tavily Web Search (authoritative SAP domains)
                           │
                           ▼
                       Normalized Web Evidence
                           │
                           ▼
                       ContextBuilder (Clearly separated prompt sections)
                           │
                           ▼
                       LLM Generation (Internal vs Fallback Web context)
                           │
                           ▼
                       Grounding & Citation Alignment (Internal + Used Web citations)
```

### Key Subsystem Characteristics:
1. **Fallback Only:** Tavily search is **never** executed if internal retrieved chunks meet the sufficiency threshold (`top_score >= settings.SIMILARITY_THRESHOLD`, default: 0.60). Internal RAG remains the primary source of truth.
2. **Authoritative SAP Domains:** Searches are strictly bounded to authoritative SAP domains (`help.sap.com`, `community.sap.com`, `learning.sap.com`, `blogs.sap.com`, `sap.com`) using Tavily's `include_domains` parameter and site search prefixing. Generic web scraping and arbitrary URL fetching are prohibited.
3. **Structured Web Evidence:** Results are normalized into structured dictionaries preserving `title`, `url`, `domain`, `snippet`/`content`, and `relevance_score`. Raw API payloads are never exposed to the LLM.
4. **Clean Evidence Separation:** The `ContextBuilder` dynamically allocates token budgets between internal chunks and web evidence, enforcing unambiguous prompt boundaries:
   - When fallback is **NOT** used:
     ```
     === INTERNAL SAP KNOWLEDGE BASE ===
     KNOWLEDGE EVIDENCE:
     ...
     ```
     (Strictly **NO** `=== FALLBACK WEB EVIDENCE ===` section)
   - When fallback **IS** used:
     ```
     === INTERNAL SAP KNOWLEDGE BASE ===
     INTERNAL KNOWLEDGE BASE EVIDENCE:
     ...
     END INTERNAL KNOWLEDGE BASE EVIDENCE

     === FALLBACK WEB EVIDENCE ===
     WEB FALLBACK EVIDENCE:
     ...
     END WEB FALLBACK EVIDENCE
     ```
5. **Strict Grounding & Refusal Behavior:** System prompts instruct the LLM to differentiate internal knowledge base from fallback web evidence. If both internal RAG and web fallback lack sufficient evidence, the LLM explicitly returns:
   > *"The information is not available in the provided knowledge base or fallback web evidence."*
6. **Citation Alignment Precision:** `align_web_sources()` inspects the generated answer for substantive mentions of titles, domains, or key phrases from web evidence. Citations are attached **only** if actually utilized in the answer. On refusals, zero citations and a 0.0 grounding score are returned.
7. **Failure Resiliency:** Gracefully traps API errors, timeouts, rate limits, and missing `TAVILY_API_KEY` without crashing or interrupting the user request. In failure cases, the system falls back to available internal chunks or standard grounded refusals.
8. **Parity Across Modes:** Shared orchestration helper `prepare_context_and_sources()` guarantees identical sufficiency checks, fallback execution, and context assembly across both non-streaming (`generate_answer`) and streaming (`stream_answer`) endpoints.

## LLM

The backend LLM subsystem is managed via `backend/app/services/llm_service.py`:
- **Provider Abstraction:** Implements unified interfaces for Groq, OpenAI, and Local providers.
- **Default Active Model:** `openai/gpt-oss-120b` via Groq (configurable to `gpt-4o-mini` on OpenAI).
- **Streaming:** Native asynchronous provider streaming using SDK stream generators (`stream=True`).

### Strict Grounding Rules:
- The LLM must answer **ONLY** from the retrieved context provided in the prompt.
- The LLM must **NOT** supplement missing information using general or pre-trained knowledge.
- If the retrieved context does not contain sufficient information to answer the user's question, the assistant must explicitly state:
  > *"The information is not available in the provided knowledge base."*
- The model must never hallucinate SAP transaction codes, database tables, function modules, or configuration steps not grounded in evidence.

## Streaming

The application utilizes **real Server-Sent Events (SSE)** and native provider token streaming. There is no artificial delay, no fake word typing, and no client-side simulated streaming.

### Verified SSE Event Protocol:
1. `event: metadata`
   - Emits structured metadata before or alongside token generation:
   ```json
   {
     "message_id": "uuid",
     "source_type": "knowledge_base" | "web" | "refusal" | "error",
     "grounding_score": 0.85,
     "citations": [...],
     "web_sources": [...]
   }
   ```
2. `event: token`
   - Emits real-time tokens as yielded by the LLM inference provider:
   ```json
   {
     "token": "..."
   }
   ```
3. `event: done`
   - Signals normal completion of the stream:
   ```json
   {}
   ```

## Architectural Decisions

The following architectural principles must be maintained:

1. **Retrieved Chunks Are Internal Context Only:** Raw retrieved chunks are never displayed directly as the answer.
2. **User Answers Generated by LLM:** The final user-facing response must always be synthesized by the LLM from the context.
3. **No Raw Chunk Passthrough:** Answers must not be raw copies or un-synthesized lists of document excerpts.
4. **No Fake Streaming:** Use only true provider streaming and real SSE events; never implement fake timers or client typing simulations.
5. **No Unnecessary Agent Swarm:** Do not introduce multi-agent frameworks or unnecessary agent swarms where a deterministic service or single prompt suffices.
6. **Preserve Working Architecture:** Do not modify working retrieval, reranking, or streaming architecture without a concrete reason.
7. **Production-Grade, Avoid Premature Overengineering:** Favor clean, maintainable, standard Python and TypeScript code over elaborate speculative abstractions.
8. **Separation of Concerns:** Keep frontend and backend responsibilities strictly decoupled.
9. **No General Knowledge for Grounded Queries:** When answering knowledge-base questions, the model must strictly decline or state missing information rather than drawing on pre-trained ungrounded knowledge.
10. **Business Data via Tool Abstraction:** Agents and APIs access operational SAP data exclusively through the `BusinessDataTool` boundary, never reading raw JSON or coupling directly to storage mechanisms.
11. **No Data Layer Fabrications:** The data layer returns only verified structured records and never fabricates explanation text or reasons for unbacked discrepancies.
12. **Tavily as Fallback Only:** Web search is strictly a fallback when internal evidence is judged insufficient (`top_score < SIMILARITY_THRESHOLD`), never replaces internal curated documentation, and never executes when internal evidence is sufficient.

## Known Issues & Current Limitations

- **Tavily API Key Dependency:** Live web search fallback requires a valid `TAVILY_API_KEY` (or legacy `WEB_SEARCH_API_KEY`) in the environment; when absent or invalid, the system gracefully handles the error and relies solely on available internal evidence or standard grounded refusal.
- **Web Snippet Quality:** Tavily search results provide snippets rather than full web pages; concise snippets may occasionally lack obscure SAP technical parameters.
- **SQLite Fallback Capabilities:** The local SQLite fallback database does not support `pgvector` HNSW cosine indexing or PostgreSQL GIN full-text search; PostgreSQL container on port 5434 is required for full hybrid retrieval.
- **Mock Data Only:** Real SAP API connectivity and user CSV/JSON import adapters are not yet implemented.
- **No Autonomous Agent / Tool Calling Yet:** The Orchestrator and Billing Investigation Agent are not yet implemented; the business-data tool is currently invoked programmatically via services and API endpoints.
